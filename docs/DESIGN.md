# 개발 전 설계안

## 범위

PM 규격 갱신: 고정된 케이크의 윗면·옆면 드로잉이 첫 MVP다. 운반, 펜 자동 교체, 출고는 후속 단계다. 기존 run3에서 검증한 것은 윗면이며 옆면 곡면 변환과 로봇 자세는 추가 개발·검증이 필요하다.
승인된 화면을 React·TypeScript로 이전하고 FastAPI 그림 검증·저장·조회 서버를 구현했다. ROS 브리지와 HMI API는 제외한다.

## 기술 제안

React + TypeScript + Vite로 웹을 구성하고 Canvas와 Pointer Events로 터치·펜 입력을 받는다.
FastAPI는 주문·그림 API를 제공하고 SQLite는 주문과 원본 그림 좌표를 저장한다. 작업 로그 API는 아직 구현하지 않는다.
HTTP로 그림을 접수한다. HMI는 정적 예시 화면이며 폴링하지 않는다. /drawing/order 발행은 후속 ROS 통합 단계다.
실물 모드와 데모 모드는 화면과 데이터에서 구분한다. 실제 로봇 연결은 ROS 측 응답으로 확인한다.

## 고객 키오스크

백화점 식품 행사에 어울리는 절제된 제과 브랜드 스타일을 사용한다.
명료한 한국어 제목, 따뜻한 화이트 작업 배경, 코랄색 주요 버튼과 흰색 캔버스를 사용한다.
큰 그림 영역과 큰 터치 버튼, 명확한 단계 안내에 집중한다.
시작 → 그림 작성 → 미리보기·확인 → 접수·제작 상태 흐름으로 구성한다.
그림 영역 밖 입력 방지, 획 되돌리기, 전체 지우기, 오류 시 그림 보존을 계획한다.
장식용 지표 카드, 과도한 그라데이션, 불필요한 애니메이션과 기술 용어는 배제한다.
브랜드명과 최종 색상은 구현 전 화면 시안에서 조정 가능하다.

## 관리자 HMI

장시간 운영을 위한 밝은 회색 배경과 높은 대비의 정보 중심 화면으로 구성한다.
상단에는 실제/데모 모드, 로봇 연결, 현재 작업 상태를 고정 표시한다.
대기 주문 표, 현재 작업 상세·경로, 시간순 이벤트·오류 로그를 중심으로 배치한다.
상태는 색과 문구를 함께 표시한다. 연결 끊김·오래된 데이터는 명시한다.
제작 시작·취소 등 운영 기능은 고객 화면과 분리한다.
웹 중단 요청은 물리적 비상정지와 다른 기능으로 표시한다.
고객 화면과 API·데이터 모델은 공유하되 레이아웃과 시각 스타일은 분리한다.

## 현재 데이터 흐름

태블릿 → HTTP/JSON → FastAPI 검증 → SQLite 저장 → 주문 ID 응답.
HMI는 예시·미연결 정적 화면이며 상태 조회 API를 호출하지 않는다.
실행 가능한 로봇 경로로의 변환, ROS 브리지와 상태 회신은 아직 연결하지 않았다.
최신 필드 계약은 DRAWING_PROTOCOL.md, 서버 구현 범위는 BACKEND_PLAN.md를 참고한다.
